# 공개 조회 화면 시안 (2026-10-15, 1차)

> **보류 (2026-10-15):** 사용자가 목록 중심 대신 연결 그래픽 중심(마인드맵, 선의 종류와 색으로 구분, 최소 글자)을 요청해 2차 시안 [transfer-map](../transfer-map/)으로 넘어갔습니다. 이 폴더의 의미 토큰·데이터·상태 처리·관리자 공통안은 2차 시안이 그대로 씁니다. 1차 화면 3종의 스크린샷은 일부만 찍었습니다(01 전체, 02 일부, 03 데스크톱, 관리자 데스크톱).

[UX UI 설계 요청서](../../ux-ui-request.md)에 따라 만든 공개 조회 화면 시안 3종과 관리자 예외 검토 공통안 1종입니다.
세 시안은 같은 합성 데이터와 같은 상태 문구를 쓰고, **정보 구조와 탐색 방식**만 다릅니다. 아직 선택 전이며, 고른 뒤에 운영 구현을 시작합니다.

| 폴더 | 내용 |
| --- | --- |
| [concept-01](concept-01/) | 구단 장부형. 구단 색인, 이적 표, 상세 칸이 한 화면에 나란히 놓인다 |
| [concept-02](concept-02/) | 변화 기록형. 첫 화면은 구단의 날짜별 변화 기록이고, 상세는 타임라인 한 줄로 읽는다 |
| [concept-03](concept-03/) | 근거 비교표형. 행을 펼치면 출처별 주장 표가 나오고, 이적 건 2~3개를 나란히 비교한다 |
| [admin](admin/) | 관리자 예외 검토 공통안. 대기열, 지금 상태와 새 주장 비교, 승인·수정·반려, 처리 이력 |
| shared | 공통 의미 토큰과 배지(`base.css`), 합성 데이터(`data.js`), 문구·날짜·가짜 조회 API(`model.js`), 공통 문구 조각(`parts.js`), 검토 도구(`review.js`) |

## 실행 방법

저장소 루트에서 정적 서버를 띄우고 엽니다.

```powershell
python -m http.server 8731 --bind 127.0.0.1
# http://127.0.0.1:8731/docs/ux-concepts/transfer-radar/concept-01/index.html
```

- 오른쪽 아래 **검토 도구**에서 시안 전환, 폭(1440, 768, 390, 320), 라이트/다크, 정지 화면(모션 줄이기), 데이터 묶음, 상태를 바꿉니다. 고른 값은 주소에 남아 그대로 공유할 수 있습니다.
- 데이터 묶음: 기본 14건, 대량 134건(30건씩 커서 조회), 1건, 0건.
- 상태: 첫 로딩, 필터 결과 없음, 시장 없음, 서버 오류(503), 타임아웃, 통신 실패, 요청 제한(429), 재조회 실패(이전 결과 보존), 다음 페이지 실패, 늦게 도착한 응답, 갱신 지연, 수집 중단, 갱신 상태 불명, 상세 조회 실패.
- `?embed=1`을 붙이면 검토 도구 없이 제품 화면만 보입니다. 스크린샷은 이 방식으로 찍었습니다.
- 인터넷 연결이 필요합니다. Pretendard 1.3.9(jsDelivr), Phosphor Icons 2.1.1(unpkg), 02의 시각 숫자용 JetBrains Mono(Google Fonts)를 불러옵니다. 운영에서는 패키지로 설치해 자체 호스팅합니다.
- 구단명은 실제 K리그 구단을 예시로 썼고, 선수·이적 주장·출처·날짜는 모두 가상입니다. 구단의 K리그1·2 배치는 예시이며 실제 시즌 승강과 무관합니다. 화면 머리에 "가상 선수·가상 소식, 구단명만 실제"를 표시했고, 링크는 `example.invalid`로 연결되어 열리지 않습니다.

## 요청 분석

### 사용자 작업과 화면

| 요청서의 작업 | 01 구단 장부 | 02 변화 기록 | 03 근거 비교표 |
| --- | --- | --- | --- |
| 1. 시즌·시장·구단 선택 | 머리 막대 시장 선택 + 왼쪽 구단 색인(모바일은 구단 시트) | 시장 선택 + 가로 구단 띠 | 조작 막대의 시장·구단 선택 상자 |
| 2. 영입·방출 목록과 최근 변화 | 영입/방출 전환 + 최근 갱신순 표 | 날짜별 변화 기록 + "지금 상태" 목록 | 최근 갱신순 표, 출처 주장 분포 열 |
| 3. 이적 건의 주장·출처·이력·검토 상태 비교 | 오른쪽 상세 칸(모바일 전체 화면), 정보 계통별 묶음 | 전체 화면 상세, 게시와 반영을 한 줄로 합친 타임라인 | 행 펼침 안의 출처 표, 전체 상세는 요약+출처 표 2단 |
| 4. 원문·공식 발표로 이동 | 근거마다 "원문 열기", 공식 확인 상자 | 같음 | 출처 표의 "열기" 열, 공식 확인 상자 |
| 5. 지난 시장 기록 | 시장 선택의 "지난 시장" 묶음, 읽기 전용 띠 | 같음 | 같음 |

### 보존한 의미

| 필드 | 표시 방법 (세 시안 공통) |
| --- | --- |
| `stage` | 점선 테두리 배지 + 아이콘 + "~설" 문구. `confirmed`만 꽉 찬 초록 배지와 인장 아이콘 |
| `evidence[].claimed_stage` | 근거마다 "주장한 단계" 배지. 반영 단계와 다르면 "현재 반영 단계와 다름" 표시 |
| `confidence` | 막대 3칸 + "신뢰도 낮음/보통/높음". 퍼센트·확률 표현 없음. 툴팁에 "이적이 성사될 확률이 아닙니다" |
| `review_status` | 아이콘 + 글자. 검토 대기는 주황 글자, 반박됨은 빨강 취소선, 검토 완료는 무채색(초록 사용 안 함) |
| `official_confirmation` | 초록 테두리 "공식 발표 확인" 상자, 확인 시각과 공식 발표 링크 |
| `source_count` / `independent_source_count` | "출처 22 (독립 6)". 상세에서 정보 계통별로 묶고 재게시는 접어 둔다 |
| `updated_at` | "갱신" 표기. 원문 시각은 "게시"로 구분 |
| `last_successful_sync_at` | 머리의 갱신 상태 줄. 지연·중단·불명이면 문구와 색이 바뀐다. API 응답 시각은 쓰지 않는다 |

### 예외 상태 처리 (세 시안 공통)

- **빈 결과와 실패 구분:** 결과 없음은 서랍 아이콘과 안내, 필터 결과 없음은 "조건 모두 지우기", 실패는 오류 종류별 제목과 "다시 시도"를 보여 줍니다. 오류를 빈 목록으로 보여 주지 않습니다.
- **마지막 성공 데이터 보존:** 같은 조건의 재조회가 실패하면 목록은 그대로 두고 "이전 결과를 보여 준다"는 띠와 불러온 시각을 표시합니다. 조건이 바뀐 뒤 실패하면 이전 조건의 결과를 보여 주지 않습니다.
- **늦게 도착한 응답:** 요청마다 순번을 붙이고, 렌더링 직전에 최신 순번이 아니면 버립니다(`shared/model.js`의 `createStore`). 검토 도구의 "늦게 도착한 응답" 상태에서 필터를 빠르게 바꾸면 버린 응답 수가 도구 머리에 나옵니다.
- **커서:** 필터·구단·방향·시장을 바꾸면 커서를 버리고 처음부터 조회합니다. 다음 페이지 실패 시 이미 받은 목록은 유지하고 그 자리에서 다시 시도합니다.
- **목록 위치 보존:** 시장·구단·방향·필터·검색어는 주소(`w`, `club`, `dir`, `stage`, `conf`, `rev`, `q`)에 두고, 상세는 `case`로 엽니다. 뒤로 가기로 돌아오면 같은 목록과 스크롤 위치, 누른 행으로 포커스가 돌아옵니다.
- **식별 불확실:** 선수 ID가 없으면 "선수 미확정", 구단이 없으면 "출발/도착 구단 미확인" 표시. 동명이인은 포지션과 소속을 같이 보이고 상세에서 안내합니다. 같은 선수의 다른 구단 연결은 별도 행입니다.
- **원문 접근 불가:** 링크 대신 "원문 삭제 또는 접근 불가"를 쓰고 출처·게시 시각·주장 메타데이터는 남깁니다.
- **공식 발표 뒤 상충 주장:** 공식 확정을 유지하고 "무산됐다는 새 주장을 검토 중"을 상세에 표시합니다(합성 데이터의 고은찬 건).
- **긴 이름:** 한글 30자 안팎, 영문 40자 이상 이름이 320px에서 줄바꿈되는지 확인했습니다(`word-break: keep-all`, `overflow-wrap: anywhere`).

## 시안별 설명

### 01 구단 장부형

- 의도: 요청서의 흐름(구단 선택 → 목록 → 상세)을 화면 배치로 그대로 옮긴다. 목록을 떠나지 않고 상세를 읽는다.
- 첫 화면: 왼쪽 K리그1·2 구단 색인(건수 포함), 가운데 구단명과 영입/방출 전환, 검색과 필터, 최근 갱신순 표. 행을 누르면 오른쪽에 상세 칸이 열린다.
- 모바일 읽기 순서: 서비스명, 시장, 갱신 상태, 구단명(누르면 구단 시트), 영입/방출, 검색·필터, 목록. 상세는 목록을 대신하는 전체 화면이고 "목록으로"가 같은 위치로 돌려보낸다.
- 상세: 반영 단계·신뢰도·검토, 요약, 검토 중 새 주장 안내, 공식 확인 상자, 식별 안내, 정보 계통별 근거 묶음(재게시는 접힘), 반영된 단계 변경 이력.
- 모션: 상세 칸 열림·목록 재조회의 흐림 처리만. 상태 전환 피드백이다.
- 장점: 처음 방문한 사람이 가장 쉽게 따라간다. 데스크톱에서 목록과 근거를 함께 본다. 공개 API 1.0만으로 만들 수 있다(건수 표시는 예외, 아래 추가 요구).
- 단점: "어제 이후 무엇이 바뀌었나"는 갱신 시각을 보고 직접 판단해야 한다. 768~1099px에서는 상세가 목록을 덮는다.
- 구현 부담: 하~중. 표, 상세 칸, 구단 시트, 주소 상태 동기화.

### 02 변화 기록형

- 의도: 반복 방문하는 팬의 질문 "무엇이 바뀌었나"에 첫 화면이 바로 답한다.
- 첫 화면: 위 가로 구단 띠, 왼쪽 넓은 "변화 기록"(오늘·어제·날짜별: 단계 변경, 검토 중인 새 주장, 새 이적 건), 오른쪽 "지금 상태" 목록과 필터.
- 모바일 읽기 순서: 서비스명, 시장, 구단 띠, 갱신 상태, 구단명, 영입/방출, "변화 기록/지금 상태" 전환, 선택한 쪽 내용.
- 상세: 전체 화면. 지금 반영된 단계 요약 아래 원문 게시와 단계 반영을 한 줄로 합친 최신순 타임라인. 재게시가 3건 이상 이어지면 한 줄로 접는다.
- 모션: 상태 전환만.
- 장점: 매일 들어오는 팬에게 가장 빠르다. "협상설 유지, 결렬 주장 검토 중" 같은 변화가 문장으로 읽힌다. 타임라인이 이력과 근거를 하나로 보여 준다.
- 단점: **공개 API 1.0에 구단별 변화 피드가 없다.** 서버에 피드 API를 추가하거나, 상세를 여러 번 불러 클라이언트에서 합쳐야 한다(비추천). 처음 온 사람에게는 두 칸의 관계를 이해하는 데 시간이 든다.
- 구현 부담: 중~상. 피드 API, 날짜 묶음, 모바일 칸 전환.

### 03 근거 비교표형

- 의도: 루머를 믿을지 판단하려는 사람에게 출처끼리의 비교를 가장 짧은 거리에 둔다.
- 첫 화면: 짙은 조작 막대(시장·구단·영입/방출), 왼쪽 필터 칸(단계·신뢰도·검토를 배지 모양 그대로 선택), 가운데 표. 표에 "출처 주장 분포" 열이 있어 반영 단계와 다른 주장이 있는 건을 펼치기 전에 알 수 있다.
- 모바일 읽기 순서: 막대(시장·구단 2열, 영입/방출, 읽는 법), 갱신 상태, 구단명과 필터 버튼, 카드형 행. 비교 기능은 데스크톱 전용.
- 상세: 행 펼침 안에 출처 표(정보 계통별 묶음, 반영 단계와 다른 주장 표시). 전체 상세는 왼쪽 요약·이력, 오른쪽 출처 표 2단.
- 비교: 행 왼쪽 확인란으로 최대 3건을 골라 경로·단계·신뢰도·검토·출처·공식 확인·갱신을 나란히 본다.
- 장점: 데스크톱에서 여러 선수와 출처를 비교하라는 요구에 가장 강하다. 재게시가 독립 근거가 아님이 표 구조로 드러난다.
- 단점: 모바일에서 정보가 많고 촘촘하다. 표가 낯선 사용자에게 첫인상이 딱딱하다. 주장 분포 열은 **목록 응답에 필드 추가**가 필요하다.
- 구현 부담: 중~상. 펼침 행, 반응형 표, 비교 상태, 행마다 상세 조회.

## 추천: 01 구단 장부형

- 요청서의 완료 기준(시장·구단 선택부터 원문까지 설명 없이 이어지는 흐름)에 가장 직접적으로 맞고, 현재 공개 API 계약을 거의 그대로 쓸 수 있습니다.
- 02의 장점은 01 위에 "최근 변화" 묶음을 얹는 방식으로 나중에 가져올 수 있습니다(서버 피드 API가 생긴 뒤). 03의 출처 표는 01 상세 칸의 근거 영역을 표 모양으로 바꾸는 선택지로 남깁니다.
- 반복 방문자 속도가 가장 중요하면 02를, 출처 비교가 서비스의 핵심 차별점이라고 보면 03을 권합니다.

## 추가 필드·API 요구 (공개 API 1.0에 없음)

1. **방향별·구단별 이적 건 수**: 영입/방출 전환과 구단 색인의 숫자(세 시안 공통). 없으면 숫자를 빼도 흐름은 유지됩니다.
2. **구단별 변화 피드**: 02의 첫 화면. 단계 변경(`history`)과 검토 대기 새 주장(`evidence`)을 구단·방향 기준으로 시간순 조회.
3. **목록 항목의 주장 분포**: 03의 "출처 주장 분포" 열. `claimed_stage`별 독립 계통 수.
4. **동명이인 구분 정보**: 지금은 포지션과 소속 구단만으로 구분합니다. 생년이나 등번호 같은 공개 가능한 구분 정보가 있으면 더 안전합니다.
5. **관리자 검토 API**: 대기열, 결정(승인·수정·반려)과 사유, 처리 이력. 별도 서버 범위입니다.

## 관리자 공통안

- 대기열은 사유별(상충 주장, 선수·구단 식별, 공식 발표 뒤 상충)로 묶습니다.
- 가운데에 "지금 공개된 상태"(실선)와 "새 주장"(주황 점선)을 나란히 놓고, 결정을 고르면 공개 화면이 어떻게 바뀌는지 미리 보여 줍니다.
- 공식 확정 건은 새 공식 출처 없이 단계를 바꾸는 승인을 막고, 사유 입력은 필수입니다. 식별 건은 선수·구단을 고르지 않으면 대기열에 남습니다.
- 처리 이력은 처리자를 내부 기록으로만 남기고 공개 화면에는 노출하지 않습니다. 인증과 권한은 시안에 넣지 않았습니다.

## 확인한 것

- 세 시안과 관리자안 × 라이트·다크 × 1440·768·390·320 폭(상세 열림, 대량 데이터, 지난 시장 포함)에서 가로 넘침을 쟀다. 스크롤 영역 안의 `sr-only` 요소가 문서 폭을 넓히던 문제(02의 구단 띠, 03의 표)를 고쳤다. 고친 뒤 다시 재지는 않았다.
- 콘솔 오류 0건(세 시안 첫 화면).
- 다음 페이지 실패 상태에서 받은 30건이 유지되고 그 자리에서 다시 시도하는 것을 01에서 확인했다.
- 2차 시안으로 방향을 바꾸면서 키보드 흐름, 글자 대비 계산, 디텍터는 이 라운드에서 실행하지 않았다.

## 해결되지 않은 의사결정

1. 한국어 표시명. 시안은 "K리그 이적 레이더"를 임시로 썼습니다. 브랜딩 방향과 함께 정합니다.
2. 필터 다중 선택 여부. 지금은 계약 1.0에 맞춰 범주별 단일 선택입니다.
3. 구단 엠블럼 사용 여부. 시안은 구단명 글자만 씁니다. 엠블럼은 사용 조건 확인 전에는 쓰지 않는 것을 권합니다.
4. 관심 구단 기억(브라우저 저장)을 MVP에 넣을지. 기획상 개인화는 Later 범위입니다.
5. 갱신 지연으로 판단하는 기준 시간. 서버 운영 주기가 정해진 뒤 정합니다.
6. 원문 삭제 시 남길 메타데이터의 범위(제목 포함 여부). 권리 검토 결과에 따릅니다.
7. 03의 비교 기능을 모바일에서도 제공할지.

## 사용성 검토

실사용자 테스트는 하지 않았습니다. 아래는 요청서의 두 질문에 대한 설계 검토입니다.

- 설명 없이 흐름을 따라갈 수 있는가: 01은 화면 배치가 흐름 순서와 같아 가장 유리합니다. 02는 "변화 기록"과 "지금 상태"의 관계를, 03은 표 펼침을 처음에 이해해야 합니다.
